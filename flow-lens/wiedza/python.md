### Wyjątki

### Obalone przy weryfikacji

- Django HTTP - teza: http.route dopisywany w process_response — W otel_middleware.py http.route jest ustawiany w process_view (z request.resolver_match.route); nazwa spana liczona raz w process_request przez resolve(request.path) i nieaktualizowana. Wpis poprawiony, nie usunięty.
- Django ATOMIC_REQUESTS - teza: async view + flaga = aplikacja nie startuje — make_view_atomic wywoływane per request w _get_response; RuntimeError leci przy każdym requeście na ten widok (500), nie przy starcie. Poprawione.
- Django management commands - teza: LabelCommand usunięte w 1.10 — Dokumentacja (stable) nadal opisuje LabelCommand i AppCommand; w 1.10 usunięto NoArgsCommand i optparse option_list. Poprawione.
- pika - teza: nazwa spana od exchange ("{exchange lub routing_key} receive") — utils._get_span: nazwa = properties.type, a gdy go brak - task_name, którym instrumentor przekazuje consumer_tag; exchange/routing_key to tylko atrybut destination. Exchange w nazwie dotyczy aio-pika, nie pika. Poprawion…
- Celery OTel - teza: atrybut messaging.message.id — Instrumentacja używa starej konwencji messaging.message_id (task_id). Poprawione.
- kafka-python OTel - teza: atrybuty z offsetem, consumer group i message id '{topic}.{partition}.{offset}' — _enrich_span w kafka-python ustawia tylko messaging.system, messaging.destination, messaging.kafka.partition, messaging.url; offset/klucz są w aiokafka. Poprawione.
- confluent-kafka OTel - opis tylko spana '{topic} process' — Jest też zewnętrzny span 'recv' wokół poll()/consume(); process powstaje dla pierwszego rekordu batcha i kończy się przy następnym poll/consume/close. Uzupełnione.
- FastAPI - teza: kod po yield 'FastAPI <0.106: po wysłaniu odpowiedzi', bez dalszej historii — Wg dokumentacji: <0.106 po odpowiedzi, 0.106-0.117 przed wysłaniem odpowiedzi, 0.118+ znowu po odpowiedzi, 0.121+ Depends(scope='function'). Poprawione.
- FastAPI - teza: Starlette ustawia scope['route'] — scope['route'] ustawia FastAPI (APIRoute); kod OTel ma TODO, że w Starlette nie da się pobrać trasy ze scope i sam iteruje app.routes. Poprawione.
- Access log - teza: przy Gunicorn+UvicornWorker gunicorn.access zwykle nieużywany — uvicorn/workers.py przypisuje loggerowi uvicorn.access handlery gunicorn access_log; linie trafiają tam w formacie uvicorna. Moduł deprecated na rzecz pakietu uvicorn-worker. Poprawione.
- SQLAlchemy after_commit - teza: SQL w handlerze otwiera nową transakcję (autobegin) — Wg dokumentacji session events sesja w after_commit nie jest w aktywnej transakcji i nie może emitować SQL (błąd stanu 'committed'); SQL wymaga osobnej sesji/połączenia. Poprawione.
- Legacy Django - teza: starsze wydania contrib = minimum Python 3.6+ (jako dowód braku OTel) — Nie potwierdzono w źródłach minimum starszych wydań; potwierdzone tylko main: django >= 2.0, requires-python >= 3.10. Teza złagodzona do 'sprawdzić package.py konkretnej wersji'.
- Django HTTP - przykład nazwy spana '^api/users/...' dla routera pod include — Django przy sklejaniu route zagnieżdżonych obcina wiodący '^' podwzorca, więc pod include('api/') będzie 'api/users/(?P<pk>[^/.]+)...'; '^' zostaje tylko dla routera w głównym URLconf. Poprawione.

### Wyjątki

- **Django ORM: logger django.db.backends (CursorDebugWrapper)**: Na produkcji DEBUG=False i logger milczy, choć skonfigurowany
- **Django ORM: logger django.db.backends (CursorDebugWrapper)**: Zapytania przez surowe połączenie sterownika (connection.connection.cursor(), własny psycopg2.connect) omijają CursorWrapper
- **Django ORM: logger django.db.backends (CursorDebugWrapper)**: QuerySet jest leniwy: SQL wykonuje się przy iteracji/len/bool/slice, często w szablonie lub serializerze, a nie w metodzie, która zbudowała filter()
- **Django ORM: logger django.db.backends (CursorDebugWrapper)**: connection.queries ograniczone do 9000 wpisów (Django 1.8+) i czyszczone przez request_started (reset_queries)
- **Django ORM: logger django.db.backends (CursorDebugWrapper)**: Django <1.8: connection.queries to lista bez limitu; DEBUG=True w długim procesie (worker, command) rośnie w pamięci bez końca
- **Django ORM: logger django.db.backends (CursorDebugWrapper)**: COPY jest logowany przez CursorDebugWrapper backendu postgresql (copy_expert/copy_to w psycopg2, copy w psycopg3), ale NIE przechodzi przez execute_wrappers; copy_from w psycopg2 nie jest logowany wcale
- **Django ORM: logger django.db.backends (CursorDebugWrapper)**: callproc nie jest logowany w żadnej wersji (w 1.6/1.7 komentarz 'callproc isn't instrumented at this time'; w 2.0+ CursorWrapper.callproc woła cursor.callproc bez debug_sql i bez wrapperów)
- **Django: execute_wrapper / CaptureQueriesContext / assertNumQ**: execute_wrappers są na obiekcie połączenia, a połączenia są per wątek: wrapper z wątku requestu nie widzi SQL z wątku sync_to_async (async ORM Django 4.1+: aget/afilter/async for) ani z ThreadPoolExecutor
- **Django: execute_wrapper / CaptureQueriesContext / assertNumQ**: Wrapper nie obejmuje cursor.callproc() ani COPY
- **Django: execute_wrapper / CaptureQueriesContext / assertNumQ**: Silk widzi tylko SQL z ORM (SQLCompiler.execute_sql); raw() przez RawQuerySet i connection.cursor().execute() do Silk nie trafiają
- **Django: execute_wrapper / CaptureQueriesContext / assertNumQ**: debug-toolbar opakowuje connection.cursor()/chunked_cursor() (widzi też raw cursor), ale tylko w procesie i requestach, gdzie toolbar jest aktywny (INTERNAL_IPS, SHOW_TOOLBAR_CALLBACK)
- **Django: execute_wrapper / CaptureQueriesContext / assertNumQ**: Sqlcommenter włączony jednocześnie w DjangoInstrumentor i w Psycopg2Instrumentor dokleja dwa komentarze
- **Django: raw SQL, procedury, widoki (managed=False), RunSQL, **: Model managed=False wskazuje na widok z triggerami INSTEAD OF albo na tabelę innej aplikacji
- **Django: raw SQL, procedury, widoki (managed=False), RunSQL, **: SQL budowany f-stringiem/konkatenacją: brak parametrów, statyczna analiza tekstu SQL niemożliwa
- **Django: raw SQL, procedury, widoki (managed=False), RunSQL, **: QuerySet.iterator() na PostgreSQL używa server-side (named) cursora: w logu Django jedno zapytanie, w bazie DECLARE + seria FETCH

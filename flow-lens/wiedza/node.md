### Wyjątki

- **Express: wejście HTTP (app.METHOD / Router / app.use) + wars**: Spany express powstają tylko wtedy, gdy istnieje span nadrzędny (kod: if (trace.getSpan(context.active()) === undefined) return original.apply(...)). Gdy instrumentacja http nie zadziała (ESM bez loadera, http zaimportow…
- **Express: wejście HTTP (app.METHOD / Router / app.use) + wars**: instrumentation-express starsza niż 0.49.0 nie obsługuje Express 5 (zakres był <5). Nie powstają spany express, a span HTTP nie dostaje nazwy z trasą (zostaje 'GET').
- **Express: wejście HTTP (app.METHOD / Router / app.use) + wars**: Bardzo stara instrumentation-http (experimental <=0.33) nazywa span serwera 'HTTP GET' / 'HTTPS GET' i nie podmienia nazwy na trasę (updateName z route pojawia się od ok. 0.34–0.36).
- **Express: wejście HTTP (app.METHOD / Router / app.use) + wars**: Anonimowe middleware i handlery: express.name to '<anonymous>' albo nazwa zmiennej. Arrow functions w app.get('/x', async (req,res)=>...) nie mówią, która klasa obsługuje wejście. routing-controllers/tsoa owijają metody …
- **Express: wejście HTTP (app.METHOD / Router / app.use) + wars**: Trasy rejestrowane dynamicznie (pętle po tablicy, fs.readdirSync + require, app.use(prefix, require(file))), sub-app (app.use('/admin', adminApp)) i router.param. Statyczny regex nie złoży z nich pełnej ścieżki.
- **Express: wejście HTTP (app.METHOD / Router / app.use) + wars**: Express 5 zmienił składnię ścieżek (path-to-regexp v8): '*' musi mieć nazwę ('/*splat'), a '?' zastąpiono '{...}'. Regexy pisane pod Express 4 dają błędne ścieżki. Instrumentacja filtruje też wildcardy v5 w http.route (f…
- **Express: wejście HTTP (app.METHOD / Router / app.use) + wars**: W Express 4 błędy async handlerów nie trafiają do error middleware bez express-async-errors albo try/catch, więc request może wisieć bez odpowiedzi. Express 5 sam przekazuje odrzucone Promise do next(err).

### Wyjątki

- **Mapa dróg do bazy w Node: statyczne rozpoznanie warstwy dany**: TypeORM i MikroORM mają identyczne nazwy dekoratorów (@Entity, @ManyToOne, @InjectRepository)
- **Mapa dróg do bazy w Node: statyczne rozpoznanie warstwy dany**: MikroORM 7 przeniósł dekoratory do osobnego pakietu @mikro-orm/decorators (podścieżki /legacy i /es)
- **Mapa dróg do bazy w Node: statyczne rozpoznanie warstwy dany**: TypeORM 0.2: dostęp do danych przez globalne funkcje (getRepository(X), getManager(), getConnection().query) bez DI. Pola z typem Repository<T> nie występują
- **Mapa dróg do bazy w Node: statyczne rozpoznanie warstwy dany**: Dostęp do danych przez HTTP/SOAP/gRPC (node-soap createClientAsync, axios do innego serwisu, Hasura/PostgREST, Supabase JS supabase.from('t').select()) wygląda jak repozytorium, ale SQL nie wychodzi z tego procesu
- **Mapa dróg do bazy w Node: statyczne rozpoznanie warstwy dany**: PrismaService extends PrismaClient: wywołania mają postać this.prisma.user.findMany(), więc w grafie nie ma klasy UserRepository
- **Mapa dróg do bazy w Node: statyczne rozpoznanie warstwy dany**: LoopBack 3/4: repozytorium (DefaultCrudRepository, Model.find w LB3) nie ma w kodzie żadnego sterownika ani SQL, bo konektor (loopback-connector-postgresql/mysql) dostarcza sterownik pośrednio
- **TypeORM: logging/logger, format '-- PARAMETERS', debug names**: Repository.save() robi najpierw SELECT po PK (żeby ustalić, czy INSERT, czy UPDATE), domyślnie opakowuje operację w transakcję (START TRANSACTION/COMMIT, opcja transaction domyślnie true) i potrafi zrobić ponowny SELECT …
- **TypeORM: logging/logger, format '-- PARAMETERS', debug names**: save() encji bez zmienionych pól wykonuje tylko SELECT, bez transakcji i bez UPDATE
- **TypeORM: logging/logger, format '-- PARAMETERS', debug names**: Instrumentacja OTel nie patchuje InsertQueryBuilder/UpdateQueryBuilder/DeleteQueryBuilder.execute() (patchuje tylko metody SelectQueryBuilder i EntityManager)
- **TypeORM: logging/logger, format '-- PARAMETERS', debug names**: Instrumentacja OTel patchuje tylko DataSource.query ('raw query'); manager.query(), repository.query() i queryRunner.query() nie dostają spanu typeorm
- **TypeORM: logging/logger, format '-- PARAMETERS', debug names**: TypeORM 0.2.x nie ma wsparcia w instrumentation-typeorm (>=0.3.0); transakcje deklaruje się dekoratorami @Transaction()/@TransactionManager() (usunięte w 0.3)
- **TypeORM: logging/logger, format '-- PARAMETERS', debug names**: Logger 'formatted-console' formatuje SQL wieloliniowo i koloruje, więc parser jednoliniowy rozbija jedno zapytanie na kilka rekordów
- **TypeORM: logging/logger, format '-- PARAMETERS', debug names**: Przy maxQueryExecutionTime wolne zapytanie pojawia się w logu dwa razy ('query:' i 'query is slow:'), a przy logging: false tylko jako 'query is slow:'

- **Prisma: log events ($on('query')), $extends query hooks, $tr**: Wewnątrz interactive $transaction kod używa `prisma` zamiast `tx`, więc zapytanie wychodzi POZA transakcją (osobne połączenie)

### Obalone przy weryfikacji

- (twierdzenie, wpis Prisma poprawiony) '$use usunięte w v7' — Middleware prisma.$use zostało usunięte w Prisma 6.14.0 (release notes: 'Removed middleware from Prisma Client (i.e. the prisma.$use method), which was deprecated since v4.16.0'), nie dopiero w v7.
- (twierdzenie, wpis Prisma poprawiony) 'tracing wymaga previewFeatures w v4.2–6.1' — Tracing jest GA od 6.1.0. Preview był potrzebny w 4.2.0–6.0.x.
- (twierdzenie, wpis Kysely poprawiony) 'domyślny log wypisuje osobno parametry i czas' — defaultLogger w src/util/log.ts drukuje tylko `kysely:query: <sql>` i `kysely:query: duration: Nms`. Parametrów nie wypisuje.
- (twierdzenie, wpis TypeORM poprawiony) span 'query' dla surowych zapytań — W instrumentation-typeorm span DataSource.query nazywa się 'raw query'. EntityManager.query/Repository.query nie są patchowane wcale.
- (twierdzenie, wpis drivers poprawiony) nazwy spanów tedious 'execSql/callProcedure' — Nazwa spanu to `<db.operation.name> <cel>`: 'execSql <db>', 'EXECUTE <procedura>' dla callProcedure, 'BULK INSERT <tabela>' dla execBulkLoad. Patchowane są też prepare i execute.
- (twierdzenie, wpis MikroORM poprawiony) slowQueryThreshold i namespace slow-query w v5/v6 — Dokumentacja 6.6 wymienia 6 namespaces bez slow-query; slowQueryThreshold i slow-query są tylko w v7. W v5.9 są 4 namespaces.
- (twierdzenie, wpis log bazy poprawiony) 'komentarz z requestId psuje pg_stat_statements' — queryid liczony jest z drzewa zapytania, komentarze nie wpływają na niego w żadnej wersji. Problemem jest tylko zapisany tekst z pierwszego wystąpienia i nazwane prepared statements w node-postgres.
- (twierdzenie, wpis knex poprawiony) regex 'knex:query (?<sql>.+?)( trx\d+)?$' — debugQuery(sql, txId) dopisuje txId albo dosłownie 'undefined', a pakiet debug dodaje '+Nms' albo znacznik czasu. Stary regex wciąga 'undefined' do SQL.
- (twierdzenie, wpis Sequelize poprawiony) format v7 taki sam jak v6 — W @sequelize/core parametry są w postaci '; with parameters <util.inspect>', a opcjonalny queryLabel idzie w osobnej linii przed 'Executing'.

### Obalone przy weryfikacji

- pino-http: req.log ma pole reqId (regex na "reqId") — logger.js: domyślnie req.log = logger.child({ req }) – id jest w "req":{"id":N}; top-level reqId tylko przy quietReqLogger:true. Poprawiono opis, regex i przypadek testowy.
- Fastify: genReqId daje 'req-1','req-2'… (regex req-\d+) — lib/reqIdGenFactory.js (4.x i main): `req-${nextReqId.toString(36)}` – licznik base36 (req-a po req-9). Regex poprawiony na req-[0-9a-z]+.
- Fastify: requestIdLogLabel 'w v5 przez logController' / kanały tracing w Fastify 4 — logController doszedł w późnych 5.x (top-level opcje oznaczone jako deprecated), na main jest 6.0.0-alpha. TracingChannel 'fastify.request.handler' jest dopiero w v5 – w 4.x tylko 'fastify.initialization'.
- Sequelize: id transakcji to UUID (regex [0-9a-f-]{36}), logQueryParameters dokłada '; with parameters [...]' — v6 query-generator: generateTransactionId() = randomBytes(10).toString('hex') (20 hex). _logQuery dokleja '; p1, p2' bez 'with parameters'; przy benchmark:true jest tylko linia 'Executed' po zakończeniu.
- knex: komunikat knex:tx '%s: Transaction completed: %s' — Brak w lib/execution/transaction.js; są tylko 'Starting top level/nested transaction', 'releasing connection', 'not releasing external connection', 'error running transaction query'.
- OTel knex: span 'select users', atrybut knex.version — utils.getName: `${operation} ${db}.${table}`; atrybuty na main w stabilnych semconv (db.query.text, db.collection.name, db.namespace…); knex.version nie występuje w README.
- OTel pg: w nowych semconv span '<OP> <db>' zamiast 'pg.query:<OP> <db>' — getQuerySpanName na main nadal zwraca `pg.query:${command} ${db}`; zmieniły się tylko atrybuty (db.system.name, db.query.text).
- MikroORM ≥6 z Kysely / 'MikroORM (knex driver <v6)' — Knex jest w MikroORM 5 i 6; Kysely zastąpił knex dopiero w v7 (2026-03, @mikro-orm/knex → @mikro-orm/sql).
- Drizzle: begin/commit w logQuery 'do weryfikacji per driver' (jako ogólna możliwość) — Zweryfikowano w kodzie: node-postgres i mysql2 logują begin/commit/savepoint (tx.execute), postgres.js (client.begin) i better-sqlite3 (natywna transakcja) – nie.
- OTel: komunikat 'Applying instrumentation patch for module on import hook' — instrumentation.ts zawiera tylko warianty '... on require hook' / '... on instrumentation enabled' – ten sam tekst pojawia się także przy patchu ESM.
- kafkajs: domyślny log {level, label, timestamp, logger, message} + osobne pole namespace; Nest context 'KafkaServer' — loggers/console.js: level = etykieta ('INFO'), namespace wklejony w message jako '[Consumer] ...'; w Nest Logger ma kontekst 'ServerKafka' / 'ClientKafka'.
- winston: logger bez transportów 'buforuje i nic nie wypisuje' — logger.js wypisuje na stderr '[winston] Attempt to write logs with no transports, which can increase memory usage: %j' z treścią logu.
- TypeORM: 'wersje 0.3.x (kod w packages/typeorm/src na master)' — master to TypeORM 1.1.x (packages/typeorm/src); 0.3.x ma kod w src/. Numeracja savepointów różni się między tymi liniami.
- Express: 'otwieramy AsyncLocalStorage.run({flowId}) w http.server.request.start' — Kanały node:http są publikowane przez publish(), a subskrybent nie owija wywołania emit('request') – run() jest niemożliwy; działa enterWith albo patch Server.prototype.emit.
- Korelacja: 'node --cluster' jako sygnał statyczny — Node nie ma takiej flagi CLI; tryb klastra to moduł cluster / pm2 / throng.
- nestjs-core / NestJS: zakres 8–11 bez uwag o Nest 12 — Wydano Nest 12 (@nestjs/core 12.2.0, czysto ESM); instrumentation-nestjs-core obsługuje @nestjs/core >=4 <12, więc w Nest 12 nie ma spanów kontrolerów.

### Wyjątki

- **Preload pomocnika przez NODE_OPTIONS (--require / --import) **: Kontekst ALS gubi się w bibliotekach z własną kolejką callbacków (stare pule połączeń, kolejka oczekujących w pg-pool przy wyczerpanej puli, Bluebird bez async_hooks, własne EventEmittery łączące wiele requestów).
- **Preload pomocnika przez NODE_OPTIONS (--require / --import) **: Aplikacja zbundlowana (nest build --webpack, esbuild, @vercel/ncc, serverless-webpack): moduły frameworków nie są ładowane przez require/import z node_modules.
- **Preload pomocnika przez NODE_OPTIONS (--require / --import) **: Wątki (worker_threads) i procesy potomne: Worker domyślnie dziedziczy flagi rodzica, a fork/spawn dziedziczy env (NODE_OPTIONS), ale każdy ma własny ALS i własny pid/threadId.
- **Preload pomocnika przez NODE_OPTIONS (--require / --import) **: Jawne execArgv przy new Worker(...) (także pusta tablica) ZASTĘPUJE dziedziczenie flag. Biblioteki przekazują zwykle process.execArgv, które nie zawiera flag podanych przez NODE_OPTIONS.
- **Preload pomocnika przez NODE_OPTIONS (--require / --import) **: Od Node 24 AsyncLocalStorage domyślnie korzysta z AsyncContextFrame; semantyka enterWith() (szczególnie wywołanego w funkcji async albo w subskrybencie kanału) różni się od implementacji opartej na async_hooks w Node ≤ 2…
- **Preload pomocnika przez NODE_OPTIONS (--require / --import) **: NODE_OPTIONS akceptuje tylko flagi z białej listy; niektóre launchery (electron, binarki pkg/SEA) mogą go ignorować albo ograniczać.
- **Hooki ładowania modułów: require-in-the-middle (CJS) i impor**: Statyczne importy ESM w module głównym są linkowane przed wykonaniem kodu; hook zarejestrowany z poziomu aplikacji (a nie --import) widzi tylko późniejsze dynamiczne import().
- **Hooki ładowania modułów: require-in-the-middle (CJS) i impor**: import-in-the-middle bywa niekompatybilny z niektórymi pakietami (eksporty z gwiazdką, cykle, top-level await).
- **Hooki ładowania modułów: require-in-the-middle (CJS) i impor**: Kilka kopii tego samego pakietu (pg w node_modules/pg i node_modules/typeorm/node_modules/pg, pnpm workspaces).
- **Hooki ładowania modułów: require-in-the-middle (CJS) i impor**: module.register uruchamia hooki na osobnym wątku – nie można w nich mutować stanu aplikacji; registerHooks nie jest dziedziczony przez worker_threads (chyba że preload przyjdzie przez execArgv).
- **Hooki ładowania modułów: require-in-the-middle (CJS) i impor**: RITM widzi tylko wywołania require(). Pakiet CJS importowany z ESM (import express from 'express', a także pg ≥ 8.15, którego esm/index.mjs robi import '../lib/index.js') ładuje się ścieżką Module._load z translatora ESM…
- **Hooki ładowania modułów: require-in-the-middle (CJS) i impor**: Pakiety ESM-only (NestJS 12, @nestjs/cqrs 12, Prisma 7): obiekt przestrzeni nazw modułu jest zamrożony – nie da się podmienić eksportu (exports.X = ...), RITM ich nie widzi (chyba że przez require(esm), wtedy dostaje nam…
- **Hooki ładowania modułów: require-in-the-middle (CJS) i impor**: Synchroniczny loader IITM (registerHooks) na Node starszym niż 22.22.3 / 24.11.1 / 25.1.0 nie obsługuje require() wciągniętych do grafu ESM.

- **node:diagnostics_channel – zdarzenia publikowane przez Node **: als.enterWith w subskrybencie 'http.server.request.start' ustawia kontekst dla reszty bieżącego wykonania parsera – przy pipeliningu/keep-alive zdarzenia na gnieździe (np. 'data' kolejnego requestu przed jego start) mogą…

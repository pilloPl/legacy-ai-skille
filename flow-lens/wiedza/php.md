### Wyjątki

- **Laravel: wejście HTTP (routes/*.php, kontrolery, Kernel::han**: Cache tras: bootstrap/cache/routes-v7.php (route:cache, Laravel 7+; w <=6 bootstrap/cache/routes.php) — źródłem prawdy w produkcji jest plik cache, nie routes/*.php
- **Laravel: wejście HTTP (routes/*.php, kontrolery, Kernel::han**: Trasy z pakietów (Fortify, Sanctum, Horizon, Nova, Livewire v3 POST /livewire/update; Livewire v2 /livewire/message/{name}) — jedna trasa Livewire obsługuje wszystkie akcje komponentów
- **Laravel: wejście HTTP (routes/*.php, kontrolery, Kernel::han**: Route model binding i middleware mogą wykonać SQL i przerwać żądanie przed kontrolerem (404 z findOrFail w bindingu, 403 z can:)
- **Laravel: wejście HTTP (routes/*.php, kontrolery, Kernel::han**: Praca po odpowiedzi: dispatchAfterResponse(), defer() (11.23+), middleware terminate() — wykonują się w tym samym procesie po wysłaniu odpowiedzi
- **Laravel: wejście HTTP (routes/*.php, kontrolery, Kernel::han**: Brak dopasowanej trasy (404 bez Route::fallback, błąd przed routingiem) — updateName nie jest wołane, span zostaje nazwany samą metodą
- **Laravel: wejście HTTP (routes/*.php, kontrolery, Kernel::han**: Lumen: Laravel\Lumen\Application obsługuje żądanie sam (implementuje Symfony HttpKernelInterface, nie Illuminate\Contracts\Http\Kernel), trasy przez $router->get() w routes/web.php — hook auto-laravel na Http Kernel praw…
- **Laravel: wejście HTTP (routes/*.php, kontrolery, Kernel::han**: Laravel 5.0–5.2: jeden plik app/Http/routes.php i grupy middleware w Kernel::$middlewareGroups dopiero od 5.2

### Wyjątki

- **Laravel: zdarzenie QueryExecuted (DB::listen) jako główne źr**: BEGIN/COMMIT/ROLLBACK nie emitują QueryExecuted, bo to wywołania PDO::beginTransaction/commit/rollBack, a nie zapytania. SAVEPOINT trans2 też nie (createSavepoint woła getPdo()->exec).
- **Laravel: zdarzenie QueryExecuted (DB::listen) jako główne źr**: Zapytania wykonane bezpośrednio na DB::connection()->getPdo() / getReadPdo() omijają Connection::run().
- **Laravel: zdarzenie QueryExecuted (DB::listen) jako główne źr**: DB::pretend(fn) oraz `php artisan migrate --pretend` emitują QueryExecuted, ale zapytań nie wykonują.
- **Laravel: zdarzenie QueryExecuted (DB::listen) jako główne źr**: Bindings są w osobnej tablicy, a $sql zawiera '?'. toRawSql() składa tekst po stronie PHP (escaping gramatyki), więc może się różnić od tego, co dostała baza.
- **Laravel: zdarzenie QueryExecuted (DB::listen) jako główne źr**: Zapytanie zakończone błędem NIE emituje QueryExecuted: runQueryCallback rzuca QueryException, zanim run() dojdzie do logQuery().
- **Laravel: zdarzenie QueryExecuted (DB::listen) jako główne źr**: Eager loading z kluczami całkowitymi używa whereIntegerInRaw, więc ID są wpisane literalnie w SQL ('where order_lines.order_id in (5, 7, 9)'), a bindings są puste.
- **Laravel: zdarzenie QueryExecuted (DB::listen) jako główne źr**: Illuminate Database użyte samodzielnie (Capsule w Slim/starych aplikacjach) bez setEventDispatcher(): Connection nie ma dispatchera, więc QueryExecuted nie jest emitowane i DB::listen nie istnieje.
- **Laravel: zdarzenie QueryExecuted (DB::listen) jako główne źr**: Nazwa spanu OTel to tylko pierwsze słowo SQL: CTE (WITH ... SELECT), CALL, SET i zapytania zaczynające się od nawiasu dostają span 'sql' z db.operation.name = null.

### Wyjątki

- **Laravel DB::transaction / beginTransaction: licznik poziomów**: Nested commit niewidoczny w bazie: Laravel przy commit na poziomie >1 nie wysyła RELEASE SAVEPOINT.
- **Laravel DB::transaction / beginTransaction: licznik poziomów**: Retry closure po deadlocku: DB::transaction($cb, 3) wykonuje callback do 3 razy, także gdy błąd poleci z COMMIT.
- **Laravel DB::transaction / beginTransaction: licznik poziomów**: Ręczne getPdo()->beginTransaction()/commit() rozjeżdża licznik Laravela.
- **Laravel DB::transaction / beginTransaction: licznik poziomów**: Model z innym $connection albo DB::connection('x') wewnątrz DB::transaction na default to OSOBNA transakcja.
- **Laravel DB::transaction / beginTransaction: licznik poziomów**: Laravel 4.x/5.0: brak savepointów. Zagnieżdżony rollBack() tylko zmniejsza licznik (event rollingBack leci), nic nie cofa.
- **Laravel DB::transaction / beginTransaction: licznik poziomów**: Błąd współbieżności w zagnieżdżonym transaction(): licznik spada, leci DeadlockException (9.x+) albo oryginalny wyjątek (5.3–8.x), bez ROLLBACK TO SAVEPOINT i bez retry, nawet przy attempts>1 na wewnętrznym.
- **Laravel DB::transaction / beginTransaction: licznik poziomów**: Po implicit commit (DDL, TRUNCATE na MySQL) rollBack() na poziomie 0 nic nie robi, bo PDO::inTransaction() zwraca false (PHP 8). commit() natomiast rzuca 'There is no active transaction'.
- **Laravel afterCommit: kolejki, eventy, listenery, DB::afterCo**: Wyścig job vs commit: SerializesModels w workerze robi findOrFail i rzuca ModelNotFoundException albo czyta stary stan.
- **Laravel afterCommit: kolejki, eventy, listenery, DB::afterCo**: afterCommit poza transakcją wykonuje się natychmiast i inline.
- **Laravel afterCommit: kolejki, eventy, listenery, DB::afterCo**: Testy z RefreshDatabase/DatabaseTransactions: Illuminate\Foundation\Testing\DatabaseTransactionsManager pomija zewnętrzne transakcje testu (callbackApplicableTransactions()->skip(count(connectionsToTransact))) i uznaje p…
- **Laravel afterCommit: kolejki, eventy, listenery, DB::afterCo**: Callback afterCommit dopina się do ostatniej oczekującej transakcji dowolnego połączenia, nie do połączenia modelu.
- **Laravel afterCommit: kolejki, eventy, listenery, DB::afterCo**: DB::afterRollBack (12.x) poza transakcją nie robi nic: addCallbackForRollback nie woła callbacku, gdy nie ma oczekującej transakcji.
- **Laravel afterCommit: kolejki, eventy, listenery, DB::afterCo**: QUEUE_CONNECTION=sync z afterCommit (after_commit=true albo ShouldQueueAfterCommit): SyncQueue wykona job inline, ale dopiero po commicie, a nie jako zagnieżdżenie.
- **Doctrine DBAL Connection: beginTransaction/commit/rollBack, **: DBAL 3 bez use_savepoints: wewnętrzny błąd złapany w try/catch i tak zabija zewnętrzną transakcję, ale dopiero na commit.
- **Doctrine DBAL Connection: beginTransaction/commit/rollBack, **: autoCommit=false: DBAL zaraz po commit/rollback otwiera nową transakcję.
- **Doctrine DBAL Connection: beginTransaction/commit/rollBack, **: PrimaryReadReplicaConnection: beginTransaction przełącza na primary i zostaje na nim (keepReplica=false).
- **Doctrine DBAL Connection: beginTransaction/commit/rollBack, **: Inna nazwa savepointu zależnie od wersji: DBAL 2.x–3.7 'DOCTRINE2_SAVEPOINT_N', 3.8+ i 4.x 'DOCTRINE_N'.
- **Doctrine DBAL Connection: beginTransaction/commit/rollBack, **: Platforma bez RELEASE SAVEPOINT (SQL Server, Oracle): zagnieżdżony commit nie wysyła nic do bazy.
- **Doctrine ORM flush() = niejawna transakcja (UnitOfWork::comm**: postFlush nie jest 'po commit', jeśli flush był w zewnętrznej transakcji (wrapInTransaction, DoctrineTransactionMiddleware, ręczny beginTransaction): wtedy connection->commit() w UoW to tylko RELEASE SAVEPOINT (DBAL 4) a…
- **Doctrine ORM flush() = niejawna transakcja (UnitOfWork::comm**: Lazy load poza transakcją: proxy i kolekcje ładują się później jako zwykłe autocommit SELECT-y. Nie ma odpowiednika LazyInitializationException.
- **Doctrine ORM flush() = niejawna transakcja (UnitOfWork::comm**: Zamknięty EM po wyjątku w długo żyjącym procesie (worker Messenger, RoadRunner, Swoole).
- **Doctrine ORM flush() = niejawna transakcja (UnitOfWork::comm**: Pessimistic lock bez transakcji: find(..., LockMode::PESSIMISTIC_WRITE\|PESSIMISTIC_READ), lock() albo refresh z lockiem rzuca TransactionRequiredException ('An open transaction is required for this operation.').
- **Doctrine ORM flush() = niejawna transakcja (UnitOfWork::comm**: postPersist/postUpdate/postRemove działają wewnątrz otwartej transakcji flush, przed COMMIT.
- **Doctrine ORM flush() = niejawna transakcja (UnitOfWork::comm**: ORM 3: błąd z commit() (np. serialization failure na COMMIT w Postgresie, deferred constraint) wychodzi jako OptimisticLockException('Commit failed').
- **Symfony Messenger: doctrine_transaction middleware (deklarat**: Handler wywołany bezpośrednio (np. $this->handler->__invoke($cmd) w kontrolerze) albo przez inny bus bez middleware omija transakcję. To odpowiednik self-invocation, bo granica wisi na busie, a nie na klasie.
- **Symfony Messenger: doctrine_transaction middleware (deklarat**: Transport sync:// albo routing bez transportu: handler odpala się w tym samym procesie wewnątrz już otwartej transakcji wołającego (zagnieżdżenie: SAVEPOINT w DBAL 4, rollback-only w DBAL 3 bez savepointów).

- **Monolog LineFormatter / JsonFormatter: domyślny format linii**: Łańcuch wyjątków (getPrevious) jest wypisywany wewnątrz JEDNEGO wpisu jako bloki '[previous exception]', każdy z własnym [stacktrace]
